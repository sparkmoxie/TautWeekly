# TautWeekly for Plex v0.25.0

Release candidate: 2026-08-29

## Native public remote access

The native Windows and native Linux Managers can now use Tailscale Funnel for optional public HTTPS
access. A remote viewer opens the generated stable `.ts.net` address in an
ordinary browser; the viewer does not install Tailscale or connect to a VPN.
The Manager itself remains bound to `127.0.0.1`, and no router or firewall
ingress port is opened.

Install the official Tailscale client, start it, and sign in on the native
host. TautWeekly does not install Tailscale, authenticate an account, or accept
an auth key. On native Linux, authorize the fixed one-shot adapter with `sudo
tautweekly remote-access-authorize`; on Windows, each change uses the fixed
administrator-approved helper. Under **Settings > Browser access**, create and
enable a unique Manager password. Then use **Settings > Tailscale Funnel** to
enable the fixed route, complete any one-time provider approval, and Verify.
The host administrator must provide MagicDNS, HTTPS certificates, and a
matching `funnel` node attribute. Tagged service nodes require an explicit
tag-targeted attribute because the default member target is not their identity.
TautWeekly neither inspects nor edits that policy.

The shared provider-neutral controller owns the state machine, password gate,
fixed target, exact route checks, Host admission, public DNS/trusted-TLS
postconditions, and fail-closed cleanup. The browser never supplies a command,
executable, CLI argument, hostname, port, target, or path.

Funnel makes the Manager login page publicly reachable over HTTPS. Every
sensitive endpoint remains authenticated, mutations retain CSRF and exact
same-origin checks, and remote cookies remain Secure, HttpOnly, and SameSite.
There is no read-only role. This release adds no new Internet login-attempt
limiter, so use a unique Manager password and treat brute-force attempts as a
remaining risk.

## Fail-closed lifecycle

Funnel cannot be enabled without an active password lock. Disabling that lock,
using local access reset, or uninstalling first disables and verifies only the
exact TautWeekly-owned Funnel. If shutdown cannot be verified, the lock or
application remains in place. Password changes keep Funnel available and keep
the current session, while other sessions are revoked.

Normal Manager restart preserves the selected persistent Funnel route for the
next start. Explicit Windows tray Exit and installer update first disable and
verify the route. Updates preserve configuration, password verification
material, history, previews, and schedule, but Funnel remains off for explicit
re-enable. Removal preserves the private data directory after verified Funnel
cleanup. An older
exact Windows private Serve route is blocked and requires an explicit Funnel
enable migration or disable cleanup.

Native Linux explicit stop, update, access reset, adapter revocation, and
uninstall first disable and verify the exact owned route. Upgrade preserves
configuration, password verification material, history, previews, and
schedule; Funnel remains off for explicit re-enable. The root helper
accepts only the installed service UID, fixed operations, and
`http://127.0.0.1:8788`; Manager never receives root, sudo, systemd, or
general Tailscale control.

After an install or update, the Windows launcher always sends the validated
loopback Dashboard URL to the browser. Focusing an already-open Dashboard is
only a convenience; it no longer substitutes for navigation, because that
window may still contain the pre-update Manager document.

## Scope

Native Windows and native Linux support integrated public Funnel. NAS/Docker,
QNAP, Synology and other Docker-capable NAS systems, Unraid, macOS Docker
Desktop, and FreeBSD Podman keep externally managed private Serve only. Public
Funnel is explicitly refused on those container surfaces because Manager has
no Docker/Podman socket, host executable, host network, privileged mode, root
identity, auth key, or vendor control plane with which to own and prove
cleanup. The bundled userspace sidecar remains private Serve only.

For clarity, a separately managed tagged container sidecar would need both an
exact `${TS_CERT_DOMAIN}:443` `AllowFunnel=true` entry and a `funnel` node
attribute targeting its real tag. The shipped sidecars deliberately contain
neither public capability, and package tests enforce that refusal. This
container-only provider requirement is not applicable to an untagged native
Windows device and does not authorize state-file edits or device tagging.

The complete package inventory and architecture are documented in
[Remote access architecture and platform support](../REMOTE-ACCESS.md).

## Live acceptance matrix

Before merge or publication, validate with sanitized accounts and no committed
runtime state:

| Surface | Required acceptance |
|---|---|
| Windows native | Enable, provider approval, public DNS/TLS Active, ordinary remote-browser login/read/CSRF mutation/logout, local continuity, restart/update, password-disable refusal, reset, and uninstall cleanup |
| Native Linux systemd | Authorize, Enable, public DNS/TLS Active, remote and local session checks, restart preservation, stop/update/reset/revoke/uninstall cleanup, and stale/malformed helper refusal |
| Docker/NAS, QNAP/Synology, Unraid | Exact private Serve admission and disable; public operation refused; no host/socket/privilege gain |
| macOS Docker Desktop | Exact private Serve admission and disable with both supported architectures; public operation refused |
| FreeBSD Podman beta | Exact private Serve admission and disable on the documented host client; public operation refused |

Sanitized Windows network validation reproduced a stale per-hostname
control-plane condition: the original Funnel name remained public NXDOMAIN,
while a renamed host published public A and AAAA answers and both tested IPv4
edges completed trusted TLS and returned HTTP 200. Restoring the original name
reproduced NXDOMAIN; restoring the new name restored publication. The corrected
candidate also bypasses Windows NRPT/MagicDNS for its fixed public-resolver
query. This is external publication evidence, not completed Manager acceptance:
the corrected build must still show **Running** after Verify and pass the full
Windows remote-browser/session/lifecycle row before merge or publication.

[tailscale/tailscale#19508](https://github.com/tailscale/tailscale/issues/19508)
remains open and documents the broader Windows class where the local route is
configured while public DNS publication is absent.
Open [#11849](https://github.com/tailscale/tailscale/issues/11849),
[#8680](https://github.com/tailscale/tailscale/issues/8680), and
[#19290](https://github.com/tailscale/tailscale/issues/19290) demonstrate that
the same local-success/public-failure class also spans Linux, iOS, Docker
userspace networking, public DNS resolution, and CDN-edge TLS. Local
`Funnel on` is therefore insufficient on every platform. Do not create an A
record, open firewall/router ports, repeatedly reset certificates, or replace
the transport. This candidate must not be merged or published until the
corrected Windows build reports **Running** and the Windows public acceptance
row passes.
